# Pending authorizations (IMS, Db2, MQ)

The optional extension `pending-authorizations`, `app/app-authorization-ims-db2-mq`. A card network sends authorization requests over MQ, and COPAUA0C approves or declines each one, replies on the request's reply-to queue and records it in IMS database DBPAUTP0 (root PAUTSUM0 per account, child PAUTDTL1 per authorization). A user browses an account's pending authorizations from main menu option 11, opens one, and marks it as fraud, which also writes Db2 table AUTHFRDS. Nightly IMS batch jobs purge expired authorizations and unload or reload the database. All eight features run on the `legacy` and `java` targets.

## Sub-features

- `pending-auth-summary` COPAUS0C, transid `CPVS`, map `COPAU0A`. Enter an 11-digit account id: the customer, the limits and balances (from ACCTDATA, not the summary) and five authorizations per page, newest first. PF8 and PF7 page; `S` in `SEL0001`..`SEL0005` opens one in COPAUS1C; PF3 returns to the main menu.
- `pending-auth-detail` COPAUS1C, transid `CPVD`, map `COPAU1A`. One authorization's card, amounts, response and merchant. PF8 shows the next authorization of the account; PF5 toggles fraud, which LINKs COPAUS2C to INSERT the detail into AUTHFRDS (or UPDATE it on SQLCODE -803) and REPLs the detail's `PA-AUTH-FRAUD` and `PA-FRAUD-RPT-DATE`; PF3 returns to the summary.
- `auth-processor` COPAUA0C, transid `CP00`, triggered by queue `AWS.M2.CARDDEMO.PAUTH.REQUEST`. Each message is an 18-field CSV request (date, time, card, auth type, expiry, message type, source, processing code, amount, MCC, country, POS mode, merchant id, name, city, state, zip, transaction id). It reads CARDXREF, ACCTDATA, CUSTDATA and the account's summary, approves (`00`) when the amount fits the summary's credit limit minus balance (ACCTDATA's when there is no summary) or declines (`05`, reason `3100` card not found, `4100` insufficient funds), puts the reply, and ISRTs or REPLs the summary and ISRTs the detail.
- `batch-auth-purge` CBPAUP0C under PSB `PSBPAUTB` (job CBPAUP0J). SYSIN `expiry-days,chkp-freq,chkp-display-freq,debug` (`00,00001,00001,Y` in the JCL). Deletes details at least `expiry-days` old and the summary whose approved count reaches zero.
- `batch-auth-unload` PAUDBUNL under PSB `PAUTBUNL` (job UNLDPADB) writes roots to OUTFIL1 (100 bytes) and each child after its 6-byte root key to OUTFIL2 (206 bytes). DBUNLDGS under PSB `DLIGSAMP` (job UNLDGSAM) writes the same through GSAM PCBs to PASFILOP (100) and PADFILOP (200, no root key).
- `batch-auth-load` PAUDBLOD under PSB `PSBPAUTB` (job LOADPADB) ISRTs INFILE1's roots and, for each INFILE2 record, GUs its root and ISRTs the child.

## How to get to it (user POV)

- Online: sign on as `USER0001`, main menu option 11. The option reports not installed unless the region has the `pending-authorizations` extension (the suite's `install`).
- Authorizations: put a request on `AWS.M2.CARDDEMO.PAUTH.REQUEST` with a reply-to queue. On Java an admin does it over HTTP: `POST /api/mq/queues/{queue}/messages` with `{"data","correlId","replyTo"}` (MQPUT1; the trigger runs CP00 once it commits), `GET /api/mq/queues/{queue}/messages` to browse, `POST /api/mq/queues/{queue}/get` to take the oldest (204 when empty). The React page `/mq` sends a request to the request queue and shows `AWS.M2.CARDDEMO.PAUTH.REPLY`; sign on as an admin on `/` first.
- Batch: operators submit CBPAUP0J, UNLDPADB, LOADPADB and UNLDGSAM (`EXEC PGM=DFSRRC00,PARM='BMP|DLI,program,psb'`). On Java they are `LibraryJob` entries of the same names.

## Driving it with run.py

Preconditions: baseline; cases in `characterization/cases/authorization/`. Inside tmux, run every command as `env -u LD_LIBRARY_PATH python3 ...`.

- **All of it.** Run `python3 characterization/run.py --feature pending-auth-summary --feature pending-auth-detail --feature auth-processor --feature batch-auth-purge --feature batch-auth-unload --feature batch-auth-load`. Expect 28 PASS (summary 9, detail 6, processor 7, purge 3, unload 2, load 1). `main-menu-option-11-installed` (feature `main-menu`) proves option 11 reaches COPAU0A with the extension installed.
- **Install the extension.** Every suite here has `"install": ["pending-authorizations"]`. It installs COPAUS0C, COPAUS1C, COPAUS2C and COPAUA0C with transids CPVS, CPVD and CP00 (from `app/app-authorization-ims-db2-mq/csd`). Without it, the transids are not defined and option 11 is not installed.
- **Send a request.** An online step `{"do": {"mq": {"queue": "AWS.M2.CARDDEMO.PAUTH.REQUEST", "trigger": "CP00", "messages": [{"data": "<csv>", "reply_to": "AWS.M2.CARDDEMO.PAUTH.REPLY", "correl_id": "REQ0001"}]}}}` puts the messages and runs CP00 once with an MQTM naming the queue. Its observation is `mq` (per queue, what the task put: `data` with trailing spaces stripped, `correl_id`), `unread` (only when the trigger left messages), `queues` (TD writes such as CSSL), `files` and `abend`; no screen keys. The terminal is untouched, so a journey can send a request and then sign on and look (`auth-then-summary-view`).
- **Datasets.** `PAUTSUM0` (key = packed account id) and `PAUTDTL1` (key = parent account id, `PA-AUTH-DATE-9C`, `PA-AUTH-TIME-9C`) are hex-encoded seeds; diffs show keys as `acct/date9c/time9c`. `AUTHFRDS` starts empty and its diff key is the raw `CARD-NUM` + Db2 timestamp text. Seeded summaries: accounts 1, 5, 7, 13, 15-18, 23, 29-34, 38, 42, 45-48, plus a garbage root `40404040404` from the unload. Account 7 has 50 details and 13 has 58; 5, 29, 30 and 31 have one. Accounts 2 and 3 have cards but no summary.
- **Subset the IMS seed.** A setup op `"where": {"FIELD": [values]}` keeps only seed records whose decoded field matches; `[]` empties the dataset. `upsert` of a fresh segment must give every numeric field.
- **Batch.** A job adds `"psb": "PSBPAUTB"` (run as a DL/I region with that PSB's PCBs) and `"sysin": [lines]`. GSAM PCBs write to the DD from the GSAM DBD (PASFILOP, PADFILOP), bound as outputs; `{"output", "reclen", "copybook": path}` decodes a record no dataset describes. Input DDs `{"dataset": "PAUTSUM0", "as": "sequential", "seed": true, "where": {...}}` take seed records, not the run's copy. One case: `python3 characterization/run.py --case batch-auth-purge-partial-expiry`.
- **Without run.py.** `cd java && mvn verify` runs the six IMS batch goldens in `BatchGoldensIT`; `ImsJobsIT`, `PcbIT`, `MqStepIT`, `MessageQueuesIT` and `QueueApiIT` cover the jobs, DL/I, the `mq` step and the queue API.
- **Java slice.** Add `--target java`. The beans are `authorization.PendingAuthSummaryScreen` (screen `pending-auth-summary`, actions `continue` ENTER, `back` PF3, `backward` PF7, `forward` PF8), `authorization.PendingAuthDetailScreen` (screen `pending-auth-detail`, actions `refresh` ENTER, `back` PF3, `fraud` PF5, `next` PF8), `authorization.FraudRegister` (COPAUS2C) and `authorization.AuthorizationProcessor` (COPAUA0C, a `mq.TriggeredProgram` for CP00). DL/I is `dli.Dbpautp0` and `dli.Pcb` over tables `pending_auth_summaries` and `pending_auth_details`; AUTHFRDS is table `authfrds`; queues are `mq.JdbcMessageQueues` over `mq_messages`, started by `mq.MqTriggerMonitor`. The batch programs are `batch.programs.Cbpaup0c`, `Paudbunl`, `Dbunldgs` and `Paudblod` (`DliProgram`s run by `batch.ims.Dfsrrc00`). The adapter seeds the segment tables and AUTHFRDS, empties the queues, installs the suite's `install` extensions, posts an `mq` step to `POST /characterization/mq` (profile `characterization` only), and submits a `psb` job as `EXEC PGM=DFSRRC00,PARM='DLI,<program>,<psb>'` with `SYSIN DD *`.

## Gotchas

- The clock is fixed, so every detail COPAUA0C writes gets the same key. A second request for the same account, in the same trigger or a later one, gets II on the detail ISRT and logs `IMS INSERT DETL FAILED` to CSSL; the summary is still updated. Use different accounts.
- COPAUA0C pins defects: the reply length is a STRING pointer never reset, so each reply ends in a low-value (`\u0000` in `data`) and later replies in one trigger repeat the earlier ones; the summary-found flag is not reset, so a card-not-found request after a found one is approved. Under GnuCOBOL, `FUNCTION NUMVAL` of a non-numeric amount is 0, which is approved; z/OS leaves it undefined.
- COPAUS0C sends the screen on read errors and continues, so the customer-not-found message wins; PF8 after the last page shows an empty list. COPAUS1C's `AUTHCD` shows the processing code.
- CBPAUP0C tests `PA-APPROVED-AUTH-CNT` twice and never REPLs the summary. When it deletes every detail of a summary it DLETs the summary right after a GNP that returned GE, so the DLET gets DJ and the job ends RC 16 (`batch-auth-purge-summary-delete-dj`). Its checkpoint frequencies compare as text, so `00001` acts as 1000. Every seeded detail is from 2023, so any expiry value deletes them all.
- PAUDBUNL and DBUNLDGS skip the blank-key root and count children as summaries; PAUDBLOD skips an orphan child silently and reports a duplicate root or child as already in the DB.
- REPL and DLET without a held segment return DJ and do not abend; SYNCPOINT commits IMS, AUTHFRDS and syncpointed MQ together, and an abend discards them. On Java an IMS step runs in one transaction that CHKP commits, so CBPAUP0C's RC 16 keeps what it deleted. These are the harness's reading of EXEC DLI, not checked against a real IMS.
- Java keeps the defects as `@LegacyDefect` methods, listed in `java/docs/legacy-defects.md`.
